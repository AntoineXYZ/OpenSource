2016 spacecraft designer statistics: report and performance evidence

Source: AuData13.dll (2016), DqDesignAnalysis::Report at 0x1801c3bc0.
Recovered with the Ghidra MCP bridge on 2026-10-05. Report decompilation timed
out, so report-specific statements below were recovered from disassembly and
the referenced ASCII strings. Small calculator functions decompiled normally.
Companion files preserve their pseudocode and all report-local text references.

All design geometry and masses use feet, cubic feet, and pounds. Technology
levels are zero based internally; Report prints internal TL + 1 (0x1801c4274).
The boost is float(TL) * 0.05f + 1.f, not modern QualityBoostF.

Report sections, in original order:
HULL; ENGINEERING; FUEL; AVIONICS; ARMAMENT; CREW; QUARTERS; HOLD;
VEHICLE BAYS; DAMAGE CONTROL; MANUFACTURE. A leading summary identifies
DISJOINT/STREAMLINED, STARSHIP/SPACESHIP/STARBASE/SPACEPORT, technology
constraints, and estimated cost.

Performance equations (calculator addresses in DesignStatsPerformance.txt):
- Maneuver force is exactly 8137140.0f per unit. Memory 0x18023fa68 contains
  little-endian bytes 68 53 f8 4a. It differs from rounding the modern double
  force result (8137140.5f). Acceleration is units * force / Mass() * boost.
- Vertical acceleration is forward acceleration * 0.16, confirmed Report
  0x1801c62b7 and double constant 0x18023fa48. Turn rate is acceleration / 25
  degrees/sec. Report rounds displayed accelerations upward to whole m/sec².
  It labels non-stations SLOW below 200, FAST at least 500, WEAK vertically
  below 10. Station classification is separately calculated at minimum TL.
- Sensor range is units * 42500 / 2 * boost feet. Report classifies strictly
  above 9000000 feet as System Range; above 300000 as Planetary; above 42500
  as Orbital; otherwise Short. Threshold bytes are at 0x18023fa5c/64/6c.
- Capacitor capacity is powerPlantUnits * boost. Reactor fuel burn and
  power production are NOT boosted by TL. FuelBurnRate is
  units * 0.007777777966111898f, bytes bb dc fe 3b at 0x18023fa30.
  Power output is fuel burn * 10.
- FuelDensity is 4.369956970214844f pounds/ft³, bytes b0 d6 8b 40 at
  0x180213a64. Do not assume modern double arithmetic has identical rounding.
- Life support, sensors, shields, maneuver and FTL consume one unit of power
  per unit per universe day: 0.00032407406251877546f per real second.
  Rocket module 0xec uses maneuver fuel = ordinary maneuver power / 10 and
  zero maneuver power. Holding maneuver power is idling maneuver power / 10.
  Idle/holding system totals include life support, sensor, optionally shield.
- Report fuel endurance is capacity / (idle-or-holding power / 10 + rocket
  maneuver fuel), converted to real days. Report capacity at selected fuel TL
  is baseFuelVolume + floor(baseFuelVolume * TL * 5 / 100). This is the
  report-level boost; the standalone FuelCapacity getter has no TL argument.
  Holding endurance is displayed only for non-rocket modules: Report
  0x1801c7b33 compares the module with 0xec and skips holding on equality.
- FTL units required are roundf(powf(float(hullVolume)*.75f*3.1415927f,
  .33333334f)). Installed units are compared directly with this integer:
  no TL reduction (Report 0x1801c6bbf).
- Base FTL engagement power is unitsRequired - .5f. Divide by FTL boost.
  Capacitor must be STRICTLY greater than required engagement power.
  Warp module 0x104 max zero-based setting is min(TL-23,
  int((capacitor / engagementPower - 1) * .5)), or -1 when inadequate.
  Report displays maximum warp factor as setting+1. Module 0x103 uses
  setting1 if capacitor sufficient; other wormhole module uses setting0.
- MustBuildInSpace if structure is STARBASE/SPACEPORT, at least six decks,
  width >119 feet, or length >119 feet.

Weapon equations:
- For nonzero weapon units, cannons=round(units/10)+1, beam projectors=
  round(units/25)+1, launchers=round(units/90)+1, ejector racks=
  round(units/100)+1. Zero units produce zero.
- BayWeaponPower = units*10*boost. This is WEAPON OUTPUT, NOT capacitor
  consumption for a full salvo.
- Report energy-weapon consecutive full-power shots are
  floor(capacitor)/projectors (integer division, 0x1801cafc6..0x1801cafcd).
  Harvester consecutive shots are floor(capacitor)/weaponUnits
  (0x1801cce61..0x1801cce6e).
- General bay range=85000*boost feet; cannon range=16404.2*boost feet.
  Harvester range=sqrt(units*10)*100*3.28084*boost feet.
  Turret power=40*boost; turret range=3280.8398*boost feet.
- The Report switch table at 0x1801d0d50 handles energy module0xfc,
  launcher0xfe, ballistic0x105, deployment0x13f, and harvesters
  0x100/0x101/0x11b/0x121/0x123. Stale module IDs0xfd/0xff and tractor0x102
  have no branch. Report uses general bay range even for ballistic bays;
  the separate CannonBayRange helper is not called by Report.
- Example damage and radii in Report instantiate AuCombatWeapon/AuItemWeapon/
  AuItemAmmo and read commodity-specific weapon fields. Damage is not
  generically equivalent to BayWeaponPower.

Shield and armor evidence and limitation:
Report 0x1801c94fe..0x1801c96e7 obtains the selected shield module's DbCommodity.
It separately formats kinetic effect17 and energy effect16 factors:
  absorbedFraction = (ArmorEffectAbsorb(effect)+ArmorModeAbsorb(Contact=2))*boost
  fixedBlock = (ArmorEffectBlock(effect)+ArmorModeBlock(Contact=2))
                 * shieldUnits * boost
Import xrefs confirm 0x180200048=ArmorEffectAbsorb, 0x180200040=ArmorEffectBlock.
Report describes damage absorbed PER SIDE. There is no shield recharge stat in
the report. ShieldDissipatePerDamagePoint independently returns 1/(boost*10).
Original kinetic/energy commodity fields are runtime database data, not a
constant table in this DLL, and the modern weapon-effect enum/data changed.
Do not invent modern-equivalent absorption values or treat shield units
divided by dissipation as a verified 2016 report statistic.

Damage-control evidence:
HullHitPointsPerUnit at 0x180073310:
  float(armor+1) * (streamlined ? 1.1f : 1.f) * (1+TL*.05f)
  * (hullCID==0x119 ? 1.5f : hullCID==0x118 ? 1.25f : 1.f)
StructureHits 0x1800753d0: if hullVolume nonzero, max(1,
trunc(factor*float(hullVolume)/256)); otherwise zero.
NonStructureHits 0x180074ee0 sums consoles, surgeries, turrets, transporter
pads, life support, maneuver, FTL, power, sensors, shields and weapon units.
TotalHits 0x180075ae0 sums structure and nonstructure.
Report multiplies these internal counts by 10 for displayed hit points
(0x1801cf821..825 and 0x1801cf8da..de).

Report relationship/diagnostics evidence:
- FTL requires an engineer station; sensors a sensor station; shields a shield
  station; surgery a medic station; transporters their station and sensors;
  weapon bays fire control and sensors. Consoles without corresponding units
  get a Useless Without warning.
- Medic and transporter station checks are scoped to (deckByte<<8)|roomNumber,
  NOT global presence. Report records medic keys at 0x1801c8498..84b4 and
  compares surgery keys at 0x1801c9b70. It records transporter station keys at
  0x1801c852b..8545 and compares pad-room keys at 0x1801c9f01.
  SurgeryUnitForConsole at 0x180075420 matches both signed deck and room number,
  returning 0xfffe if none matches. Transporter consoles without pads are
  tested against their own room key at 0x1801c8560..85ac.
- Required minimum hull equipment: helm, life support, gravity drive, reactor,
  fuel cell, hull entrance OR transporter, contiguous hull.
- Officer stations are captain-chair consoles. Other consoles are crew
  stations. Drivers/pilots come from parked vehicle types. Turret gunners
  correspond to turrets; guards to troop stations.
- Report recommends officer berths per officer station, crew berths per crew
  station, troop berths per turret. Passenger accommodation is first class
  with galley+lounge, second class with galley, otherwise third class.
- Operable door count beyond rendering capacity gets a separate warning;
  transporter rooms with duplicate numbers warn about Beam Up ambiguity.

Information-pane presentation recovered for the F6 recreation:
- Shores of Hazeron.exe TimerUpdate 0x1402d33e0 calls the report producer at
  0x1402e7810, compares the cached QString, and updates one read-only HTML pane
  while preserving its vertical scrollbar. Tips and statistics are not tabs.
- The producer prepends yellow rgb(255,255,0) Modified when dirty. Empty
  analysis uses NEW SPACECRAFT DESIGN TIPS in the same pane.
- AuData13.dll Report strings at 0x1801c407e onward establish DISJOINT and
  STREAMLINED prefixes, uppercase classification, Tech Level, nested armor,
  mass, equipment, module and manufacturing TL requirements, then cost.
- Report uses margin-left: 10px nested divs; HULL dimensions and mass details
  are one level deeper. Section headings are uppercase bold following <hr>.
  Exact strings/order are in pseudocode/AuData13.dll_DesignStatsReportStrings.txt.
- Recreation uses zero-margin paragraphs with equivalent 10px indentation to
  preserve wrapped-line alignment in Qt rich text. Navy/pale colors and 11px
  text approximate the supplied screenshot; native font/rendering comparison
  awaits the user's manual build. Additional recovered numeric values remain
  in their corresponding sections; edit feedback is appended and in a tooltip.
- Manufacturing cost/TL and armor absorption are explicit unavailable entries,
  not constants copied from the Star Driver screenshot. The removed city
  manufacturing infrastructure is outside this change; debug spawning may
  remain necessary until that separate infrastructure is restored.

Known gaps to keep explicit:
- Manufacturing component recipes, runtime commodity production TLs and
  EstimatedCost cannot be reconstructed solely from the performance helpers.
  HighestTechLevel and InitSpacecraft provide recoverable static module and
  recipe constraints, but current cached binary metadata must not replace
  recalculation after edits.
- Commodity-specific armor/shield absorption, weapon/ammunition example
  damage, splash radius, and estimated economic cost require the 2016
  commodity dataset or a validated mapping, not modern quality scaling.
- Full original Report HTML is not decompiled; selected equations above were
  checked against machine instructions. Room/equipment aggregation is
  documented separately in DesignStatsAggregation.txt.
