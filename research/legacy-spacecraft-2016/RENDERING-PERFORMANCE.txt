2016 spacecraft designer: rendering performance evidence
=======================================================

Read-only Ghidra MCP inspection, 2026-10-05. Addresses refer to AuAtom13.dll
unless another program is named. These are recovered behaviors, not measured
frame times or claims that the current adapter already implements them.
No build, shader compilation, or original-client benchmark was initiated.

Cached geometry and few draw calls
---------------------------------
DaSpaceShip::CreateModels 0x1803df500 builds two triangle collections:
  exterior = RenderExterior(..., false)
  interior = RenderInterior(...) + RenderExterior(..., true)
The existing capture is pseudocode/AuAtom13.dll_1803df500_DaSpaceShip_CreateModels.txt.

AuGLModelMaker::SpacecraftModel 0x180145e70 looks up a model by design ID.
On a miss it creates an AuSpacecraftModel task and starts it on the global
QThreadPool, initially returning empty VAOs. Subsequent calls retrieve the
same task/cache entry. Helper 0x180140f00 waits for its completed state without
blocking (QMutex::tryLock), creates exterior/interior VAOs once using
GL_STATIC_DRAW (0x88e4), clears the CPU triangle collections, and returns the
cached VAO handles. Task constructor 0x1801382a0 initializes those collections
and identifies the task as AuSpacecraftModel.

DaSpaceShip::CreateDeviceObjects 0x1803dcb50 retains exterior/interior VAOs at
this+0xda8 and this+0xdc8. In the designer, invalid design analysis deletes
the model-maker entry and clears these handles; an unchanged design does not
rebuild its mesh every frame. Resource models use Au3dsGLSLModelCache too.

DaSpaceShip::RenderEnvironmentObject 0x180423a60 selects/draws each whole
exterior/interior VAO. AuGL13.dll AuGLVAO::DrawGL 0x180011420 issues one
glDrawArrays(GL_TRIANGLES, 0, vertexCount), so the static ship geometry uses
approximately two draws, with separate draws for consoles, guns and other
resource models. The renderer does not submit a separate static draw for
every room, item instance, or triangle.

Animation without changing vertex buffers
----------------------------------------
The recovered shaders/Spacecraft.v.glsl accepts per-vertex atlas and effect
offset indexes plus shininess. A texOff[150] uniform array packs up to 300
vec2 offsets into its xy/zw pairs. Materials and effect frames therefore
share a large static buffer instead of requiring per-instance state changes.
RenderShaderTextureOffsets 0x180444770 changes shader uniforms; the associated
static geometry stays resident. The effect texture is combined in the
fragment shader, rather than generating another mesh for each animated frame.

Culling found, and its designer exception
----------------------------------------
RenderEnvironmentObject has gameplay tests for being behind the camera,
distance-based omission of interiors/details, and a simplified far exterior.
Its DaDesignEnvironment branch bypasses those tests and explicitly enables
the near/interior rendering path. DaDesignEnvironment::RenderEnvironment
0x1802fb170 traverses its children, omits the design plane in solid mode, and
runs the RenderLast list afterward.

No per-room visibility graph, room occlusion test, or occlusion-query draw
suppression was found in these designer paths. This is scoped to the inspected
paths, not proof that no other part of the game ever used such techniques.
Back-face/depth rejection and bulk cached geometry must not be described as
recovered CPU room occlusion culling. The most directly supported performance
difference is cached, batched draws with shader-driven material animation.

Alpha testing versus genuine model translucency
-----------------------------------------------
RenderEnvironmentObject sets the unpowered exterior alpha cutoff to 0 and
the interior cutoff to 0.1, applying them to their entire spacecraft VAOs,
not just windows. Powered lighting can select 0.2, outside this empty-fuel,
empty-capacitor preview state. shaders/Spacecraft.f.glsl discards sampled
alpha <= cutoff; surviving static ship fragments are not individually sorted
or submitted in a second translucent hull pass. This includes procedural
atlas equipment, railings, doors and window frames. Effect alpha blends the
effect RGB into the surface in the shader, not the surface into the scene.

DaSpaceShip::RenderLast 0x180441350 draws contrails, transient damage effects,
and shields. It does not redraw sorted translucent hull/interior triangles.
Thus using a single alpha-tested pass for procedural spacecraft atlas geometry
matches the recovered structure and avoids needless per-frame triangle sorting.

Do not infer that all resource models should be opaque. AuGL13.dll
Au3dsGLSLModelInstance::RenderGLSLModelTex 0x180021b70 has a separate, explicit
blending path for model objects whose m_GlowColor alpha is below 1. The current
vehicle import preserves that alpha in Batch::tint.w. Such true material
translucency needs separate handling. Merely finding a non-255 pixel in an
atlas/cutout texture is not evidence that its complete mesh needs sorting.

Modern source cross-check
-------------------------
src/lib/atom/entities/vehicles/dasc.cpp, DaSc::CreateDeviceObjects, retains
GL_STATIC_DRAW geometry behind m_VAOsCreated and caches console/effect resources.
DaSc::RenderEnvironmentObject uses whole-ship behind-camera and distance tests;
these are not a reusable room visibility system for the offline designer.
DaDesigner uses the same native resource/rendering infrastructure.

src/lib/data/designs/auglmodel.h provides AuGLModelCache for named resource
models, and auglmodelmaker.cpp retains asynchronous model caches for other
modern entities. Those APIs do not accept the legacy procedural ship batches.
The adapter already caches its uploaded ship VBO and imported resources using
the modern Au3dsGLSLObject::LoadModel; native console, character, lighting and
particle renderers remain shared. Replacing its cached VBO with an AuGLVAO
wrapper alone would not remove the repeated sorting or excessive submissions.
No suitable existing conservative CPU frustum helper was found in the searched
modern rendering/math paths; selection rectangle helpers are not equivalent.

Adapter changes and manual verification
---------------------------------------
The adapter keeps its static VBO and applies the recovered single alpha-tested
pass to all procedural atlas surfaces. Imported model translucency remains in
the sorted pass. Sorted triangle depths are calculated once; the index buffer
is reused while visibility, camera, geometry transforms and opacity are stable.
Per-source texture pointers are cached, including door and console-state
variants. UV/effect animation still updates without re-uploading ship vertices.

Material batches are partitioned into 32-foot cells at upload. Each chunk's
sphere encloses every vertex of its triangles, including faces spanning cells;
six camera planes reject only wholly outside chunks. Adjacent visible ranges
are merged back into one draw. This is conservative view-frustum culling added
to the adapter, not a recovered 2016 room-occlusion algorithm. Rotating geometry
uses transformed sphere centers, and occupied consoles stay in the native pass.

Solar-disk lighting uses the equivalent cosine angle-addition identity instead
of per-vertex inverse trigonometry. Back-face lighting is only calculated for
two-sided materials. Studio light positions, ambient values, effects and
contrails are retained. Movement and targeting use separate broadphase grids;
sight rays visit crossed cells rather than their whole enclosing volume.
See WALKTHROUGH-COLLISION.txt for those independent reference checks.

After the user's manual Windows build, compare a previously slow design and
Star Driver after loading settles: stationary, turning, walking inside, looking
away from the ship, and viewing the entire exterior. Check doors/hatches,
glass/cutout edges, rotating models, console entry/exit and edits/reloads.
Geometry must not vanish at screen edges or when the camera enters a chunk.

Optional release-build diagnostics: set HAZERON_LEGACY_RENDER_STATS=1 in the
process environment before starting the client. In PowerShell:
  $env:HAZERON_LEGACY_RENDER_STATS='1'
Then launch the existing executable normally from that shell. Remove afterward:
  Remove-Item Env:HAZERON_LEGACY_RENDER_STATS
The normal Qt log/debug output gets one "Legacy render:" line per second:
paint FPS, average CPU paint duration, adapter mesh draws/triangles, visible
ranges, total chunks and transparency rebuild count. Draw/triangle counters
exclude native sky, console, particle and HUD draws. CPU paint time is not a GPU
timer and may include driver stalls; loading is not a steady-state measurement.
Counters reset when switching render mode. With a stationary camera and static geometry,
transparency rebuilds should drop to zero after the first applicable frame.

Read-only validation
--------------------
Independent numerical comparisons of the lighting identity covered 100,000
random cases, with maximum double-precision discrepancy below 9e-16. Frustum
checks used float32-style sphere/plane arithmetic against an independent
homogeneous triangle-clipping oracle: 13,920 chunks / 45,974 triangles across
160 cameras, including huge triangles, camera-enclosing bounds, near/eye-plane
crossings, negative coordinates and pivot rotations. All 5,932 chunks with
visible clipped geometry survived. Source review covered buffer offsets,
cache invalidation, GL state after native draws, C++11/Qt5 usage and whitespace.
These are algorithm/source checks, not executed C++ or GLSL validation.

Recovery limits
---------------
These findings support reducing draw/state-change counts, preserving GPU
buffers across unchanged frames, and avoiding static atlas transparency sorts.
They do not identify the user's actual CPU/GPU bottleneck without runtime
measurements, and no numerical frame-rate improvement is claimed here.
