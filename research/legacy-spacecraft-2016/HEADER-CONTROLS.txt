Original 2016 ship header controls
=================================

Evidence: pseudocode/ship-header-control-evidence.txt and the previously
captured DnSpaceShip working constructor and SetArmor/Streamline functions.
All addresses below are from the original 2016 DLLs, read-only in Ghidra.

Streamline is a Boolean UI choice. DaSpaceShip::SetDesignStreamline(bool),
AuAtom13.dll 0x1804618b0, accepts a bool and delegates to the data layer.
The stored design field is a byte at DnSpaceShip +0x14. Its data-layer
setter, AuData13.dll 0x180149f90, accepts a byte and changes the design only
when its value differs. The decompiler labels its tiny shared field-store
callee AuItem::SetHitPoints; that is an alias from identical machine code,
not evidence that this control changes hit points. The getter is
AuData13.dll 0x18014a090. A checkbox is faithful to the original UI-facing
API; the modern designer's multivalue streamline selector is not evidence
of a multivalue 2016 control.

Armor increments and decrements by one. The data-layer increase function
at AuData13.dll 0x180144420 refuses a change when the existing byte is >=10.
The decrease function at 0x180144320 refuses a change when it is zero.
Thus the original controls produce values from 0 through 10 inclusive.
The low-level DnSpaceShip::SetArmor(short), 0x18017e3a0, merely narrows and
stores at +0x15; it does not itself enforce the UI range. Do not silently
normalize unusual pre-existing file bytes merely by displaying a control.

Both data-layer controls reject read-only designs and notify the global
design-change handler when they change a field. DaSpaceShip wrappers for
armor decrease/increase (AuAtom13.dll 0x1804615d0/0x1804616c0) and streamline
also check CanDesignBeModified and invalidate cached ship geometry/path
after a successful change.

The new working-design constructor at AuData13.dll 0x180178f70 writes the
little-endian ushort 1 at +0x14: streamline defaults to true (1), armor to
zero. These are new-design defaults; loading must retain file values.

The recovered wall-profile and rendering routines consume these fields:
streamline changes exterior-wall construction and armor changes profile
strips/window availability. Exact original 3D rendering is deferred; see
SURFACE-RECOVERY-NOTES.txt. The interface controls can still edit their
actual design fields without claiming that a 2D view shows those effects.
